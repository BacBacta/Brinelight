| 2026-10-16 | Online: one Hetzner CX23 (Ubuntu 24.04, Germany) running Docker Compose (`deploy/`): PostgreSQL 18.6, the game server (Node 22.23.2, `tsx`, user without rights) and Caddy 2.11.4, with exact image versions updated on purpose (docs/deploy.md). Only Caddy opens ports (80, 443); the database is on a network without Internet access. The domain `brinelight.xyz` stays at Vercel with its DNS: `api` is an `A` record straight to the server (Vercel DNS has no proxy; no AAAA), `play` a `CNAME` to `brinelight.pages.dev`, added only after the custom domain is set up in Cloudflare Pages; the bare domain is not used for now; Caddy is the only proxy trusted for X-Forwarded-For. SSH by key only, no root login, `ufw limit 22/tcp`, automatic security updates. Nightly `pg_dump` kept 7 days on the server, plus Hetzner Backups of the whole machine. In production the server refuses to start without `DATABASE_URL` and `ALLOWED_ORIGINS`. | One small machine is enough for now and stays cheap; the two kinds of backup cover both a data mistake and the loss of the server; the CI starts the same stack on every push. |
| 2026-10-15 | Sign-in from the game (`client/src/account/`): the session token is kept in localStorage (`brinelight-account-v1`) this week, to be reviewed before payments (week 13) with a cookie on a shared domain. The city in play is always saved on the device; before the account city takes its place, the device's city is copied to `brinelight-client-v1-before-sign-in`, and signing out forgets only the token. The city is sent to the account every 30 s and when the page is hidden, only after an action or an event (a job started or finished, a fleet step, a report read), not for the passing of time, which the server computes; and at least every 30 min while playing, so the server never counts less time than was played. | Nothing is ever lost by signing in or out; saves stay few (6 per minute at most on the server). |
| 2026-10-15 | The save sent when the page is hidden uses `fetch` with `keepalive` and `Authorization`: the end-to-end test checks, with the CORS preflight held 800 ms, that it reaches the server after the page has gone, which a plain fetch does not. The page never sees that answer, so the client notes the version a save left from (`pending`) and, at the next load, an account one version ahead is recognized as its own save, without a conflict message. | Closing the tab must not lose the last change nor show "Your city changed on another device" on the next visit. |
| 2026-10-15 | `POST /auth/nonce` gives the `issuedAt` in whole seconds (stored with the nonce, column `issued_at`; compared as an instant, so "12:00:00Z" and "12:00:00.000Z" are the same), `chainId` and `statement`; `/auth/verify` requires the message's Issued At to be exactly that one, and still within 5 min of the server clock. | The client writes no time, network or statement of its own: a phone with a wrong clock can still sign in, and a message cannot be made for another moment than the nonce. |
| 2026-10-15 | End-to-end tests (`npm run e2e`, `e2e/`): the server on PGlite, the built client in Chromium driven by `playwright-core` 1.56.1, and a test wallet that only offers `solana:signIn`, with its key in the test, never in the client build. Not part of `npm run check`; the CI job `e2e` does not block this week. | The sign-in can be tested without a real wallet; the job becomes required once stable. |
| 2026-10-15 | Every refusal of the server is `{ code, error }`: `code` is stable and tested by the client (`signed_out`, `version_conflict`, `invalid_city`…), `error` is the English text for the player (`server/src/refusals.ts`). | The client can react to a refusal without reading its text, and the text can change freely. |
| 2026-10-15 | `PUT /city` saves the city the client sends, for week 3 only (removed in week 4). It is checked strictly (`parseState`, nothing dropped, levels within `maxLevel`, no job on a building at its highest level, fleets within `fleetsMax`), limited to 64 KB and 6 saves per minute and per player, and never replaces an unreadable stored city. `GET /city` creates nothing and returns the city advanced to `asOf`, the server time; the client adds no time away of its own. | It goes against "the server decides", but lets a player find their city on another device this week; week 4 replaces it with actions checked by the server. |
| 2026-10-15 | The client signs in only with the Wallet Standard `solana:signIn` feature, never `solana:signMessage`. A wallet without it shows "Your wallet cannot sign in yet. Use Phantom, Solflare or Backpack." | The `Origin` header only protects inside a browser: with `signMessage`, a fake site could get a "Brinelight" message signed and replay it from a script. With `signIn`, the wallet itself checks the domain. |
| 2026-10-15 | Wallet sign-in (Sign In With Solana) is checked by the server alone, in `server/src/auth/`: the signature is verified with Node's own Ed25519 on the exact bytes the wallet returned, then the text is read strictly (each expected line once, no other line; `Expiration Time` required, at most 10 min after `Issued At`, which must be within 5 min of the server clock); domain, uri and the `Origin` header must match `ALLOWED_ORIGINS`; the chain is `SIWS_CHAIN_ID`. The nonce (5 min) is used only after the signature check, in one `UPDATE … RETURNING`. A session token is 32 random bytes, returned once, sent as `Authorization: Bearer`, stored only as its SHA-256 hash, valid 30 days; the header is redacted from logs. Base58 is our own tested function. New dependencies: `@fastify/cors` 11.3.0 (only the game's pages may call the server) and `@fastify/rate-limit` 11.2.0 (20 sign-in requests per minute per address). `TRUSTED_PROXY` (empty by default) names the only proxy trusted for X-Forwarded-For. | No Solana library for two small, well-defined checks; a signature that holds on bytes the server did not rebuild cannot be fooled by a different reading of the text; a stolen database or log gives no usable session. |
| 2026-10-15 | A city is stored as one JSON document (`cities.state`, jsonb), read and written only with `parseState`, with a version number that goes up by one on each save; a save from an older version is refused. A stored city that `parseState` refuses is never replaced: it is reported, logged with the player id only, and left as it is. | The rules work on the whole city; one document with a version is simple and safe against two devices saving at once. |
| 2026-10-15 | Database: PostgreSQL with Drizzle (`drizzle-orm` 0.45.3, `pg` 8.23.1, migrations from `drizzle-kit` 0.31.11, committed in `server/drizzle/`). Without `DATABASE_URL`, PGlite 0.5.8 runs in memory (tests, local development, CI); it is a development dependency, loaded only then. PGlite 0.5.8 is **PostgreSQL 18** (18.3): the online server (task 6) uses PostgreSQL 18 too. | No database to install for tests and CI; the same engine version in tests and in production. |
| 2026-10-15 | parseState is strict and shared (the server uses it); repairs of old local saves live only in the client (migrateSave). The player state (`PlayerState`, `advance`, `catchUp`, `upgrade`, `sail`, `readReport`) moved to `shared/src/state/`; the client keeps only the browser clock (`tick`, `elapse`, `DEV_SPEED`) and localStorage. | A city sent without Pearls or without its sea must be refused, not given 200 Pearls or full wrecks; only dropping a bad job or fleet is tolerated, since it can only make the player lose something. |
| 2026-10-15 | Cloudflare Pages builds and deploys from its Git integration (build: npm run build, output: client/dist); each branch gets a preview URL. The GitHub Actions deploy workflow was removed. | The two did the same job; the Git integration needs no secrets in the repository. |
| 2026-10-15 | Performance is measured on the phone itself with `?fps` (counter) and `?quality=0\|1\|2` (forced step); three.js gets its own build file, and the 500 kB warning is kept (`docs/perf.md`). | The goal is 30 FPS on the low-end Android test phone; the warning limit applies to every file, so raising it would hide a growth of the game's own code. |
| 2026-10-15 | The sea rules live in `shared/src/rules/sea.ts`: a fixed list of 40 sites (the prototype's seeded positions, and the amounts and city levels of one prototype game), 2 rope per wreck instead of 1 to 3, a fleet that keeps the research, lead captain and hold it left with, and no captain fragments or experience for now. `STARTING_LEAD` is Old Tom. | No randomness in the rules; the client and the server run the same trips and combats; fragments and experience come with the captains (weeks 3 to 6). |
| 2026-10-15 | The game fonts (Lilita One 400, Nunito 600 to 900) are served by the game itself with `@fontsource/lilita-one` and `@fontsource/nunito` 5.3.0, never from Google Fonts. | GDPR: loading Google Fonts sends the players' IP addresses to Google. |
| 2026-10-15 | Pearls live in the player state apart from the stock (`STARTING_PEARLS = 200` in `start.ts`); storage never caps them. | They are earned by playing and are not stored in the warehouses. |
| 2026-10-15 | The build queue is a shared rule (`startUpgrade`, `advanceQueue`, `UpgradeJob` in `shared/src/rules/buildings.ts`): a job keeps the duration fixed at its start, and jobs ending at the same moment finish in the order they were started. | The client and the server run the same queue; the client cuts production at each finished job, so time away gives the same result as playing live. |
| 2026-10-15 | Starting values of a new city (stock, troops, survivors, morale, captain) and the offline cap (8 h) live in `shared/src/rules/start.ts`, with the prototype's values. | The client and the server create the same city; no starting value is written in the client. |

- **Offline cap of 8 h: keep it or rely on storage only?** To decide in week 17.
- **A wreck refills at once when emptied: add a delay?** To decide in week 17.
- **Camp levels are per player in the client; the server will own them in multiplayer.**
